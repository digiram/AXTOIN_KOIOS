Operator

Run, configure, ship

Prerequisites

  • Node.js — LTS recommended (repo targets modern ESM TypeScript).
  • pnpm — Install via corepack enable or pnpm.io; the repo pins pnpm@10.33.2 in root package.json (packageManager).
  • Git — For cloning and updates.
  • Optional: Docker Desktop (or compatible engine) for Redis + database via Compose.
  • Mobile: Expo tooling / simulators when working on apps/mobile.

First-time install

  1. Clone the repository and open a terminal at the repo root.
  2. Copy the environment template to the repository root and edit secrets: 
    cp .env.example .env
    The API and worker load this file even when you start them from apps/api or apps/worker. Adjust database, Redis, JWT secret, and encryption key (see Environment variables).
  3. Install dependencies: 
    pnpm install
  4. Start infrastructure (pick one database profile). From the repo root: 
    # PostgreSQL + Redis + API + worker (example)
docker compose --profile postgres up --build
    Or MySQL: 
    docker compose --profile mysql up --build
    Ensure your .env matches the chosen DB (dialect, host, port, credentials).
  5. Alternatively run Postgres/MySQL and Redis yourself; point DATABASE_* / REDIS_URL at those services.
  6. Run web + API + worker together (needs Postgres/MySQL + Redis already running and .env aligned): 
    pnpm dev:all
    Runs pnpm db:migrate once, then starts Vite (typically port 5173), the API on API_PORT from .env (legacy PORT if unset), and the BullMQ worker in parallel with AUTO_MIGRATE=false on the API so it binds sooner. Set VITE_API_BASE_URL if the web app must call a non-default API origin (for example http://localhost:3500).
  7. Or run the API alone (applies migrations on startup when AUTO_MIGRATE rules allow — see Database & migrations): 
    pnpm --filter @starter/api dev
Tip: After changing schema in packages/db, use Drizzle Kit scripts (see root README) to generate new migrations; the API can apply existing migrations on boot when configured.

Environment variables

Canonical template: .env.example. Values below summarize behavior; URL composition rules live in packages/db/src/database-url.ts. Full tables: environment.md.

Core & logging

Variable Purpose
NODE_ENV Typical values: development, production. Affects defaults such as BullMQ queue prefix and AUTO_MIGRATE behavior.
API_PORT HTTP port for the Fastify API (default 3000 if unset and legacy PORT is unset). Feeds Vite’s default API URL when VITE_API_BASE_URL is unset.
PORT Legacy alias for API_PORT — used only when API_PORT is unset or empty.
CORS_ORIGINS / CORS_CREDENTIALS In production, cross-origin browser access requires a non-empty CORS_ORIGINS allowlist; if unset, CORS is denied. Non-production may use reflect mode when unset. See environment.md.
DATABASE_DIALECT mysql selects MySQL drivers + drizzle/mysql migrations; supabase selects hosted Supabase Postgres (same schema/migrations as Postgres, TLS defaults); otherwise Postgres.
DATABASE_URL Optional single connection string. If set (non-empty after trim), it overrides composed parts — use for hosted URLs, SSL query params, or IPv6.
DATABASE_HOST, DATABASE_PORT, DATABASE_USER, DATABASE_PASSWORD, DATABASE_NAME Used to build a URL when DATABASE_URL is unset. Port defaults: 5432 (Postgres), 3306 (MySQL). Password may be empty.
REDIS_URL BullMQ / ioredis connection for the worker and optional API job enqueue.
JWT_ACCESS_SECRET Secret for signing short-lived access JWTs (@fastify/jwt). In production (NODE_ENV=production) the API refuses to start unless this is set and at least 32 non-whitespace characters. Otherwise, if unset, a dev-only default is used (with a warning in logs).
JWT_REFRESH_SECRET Present in .env.example for future JWT-based refresh flows. This starter stores refresh tokens as opaque hashes in the DB, so this variable is not read by application code unless you extend it.
FIELD_ENCRYPTION_KEY Base64-encoded 32-byte key for AES-256-GCM field encryption (packages/crypto).
AUTO_MIGRATE Single migration-on-boot switch: off/false/0 never; force/always always (incl. production); dev/unset runs only when NODE_ENV is not production. Legacy truthy values (true/1) are treated as dev and rejected at boot in production — use force or off.
BOOTSTRAP_SUPER_ADMIN_EMAIL, BOOTSTRAP_SUPER_ADMIN_PASSWORD Optional API startup seed for a single platform super admin (tenant_id NULL). Idempotent: skips if that email already exists. Realm admins are not bootstrapped — use registration or your own flows.
LOG_LEVEL Pino level for API and worker (trace … silent). Overrides verbose defaults when set.
VERBOSE Set to true or 1 for debug-level output when LOG_LEVEL is unset.
LOG_PRETTY Set false to emit JSON lines in development (production always uses JSON).
LOG_HTTP Set false on the API to disable Fastify per-request access logs.

Frontends use public env prefixes where applicable (Vite VITE_*, Expo EXPO_PUBLIC_*) — see development.md.

System architecture

The repository is a pnpm workspace: applications under apps/*, shared libraries under packages/*. The API owns authentication, tenant scoping, and persistence; web and mobile are thin clients over HTTPS. Deeper diagrams and boundaries: architecture.md.

Figure: Clients talk to the API; the API uses workspace packages and persists to SQL; Redis backs BullMQ for the worker and optional async jobs from the API (dashed).

Authentication model

  • Access JWT — Short-lived, signed with JWT_ACCESS_SECRET; includes user id, tenant id, and email for downstream handlers.
  • Refresh token — Opaque random string; only a SHA-256 hash is stored. Rotation on POST /v1/auth/refresh. Production web builds may use an HttpOnly refresh cookie (see authentication.md); the SPA also mirrors refresh in sessionStorage for same-tab recovery.
  • Tenant isolation — Data rows carry tenant_id; protected routes resolve tenant from JWT and repositories scope queries accordingly.

Roles, realm vs platform login, bootstrap: authentication.md.

Database & migrations

  • Drizzle schemas and SQL migrations live under packages/db (separate folders for Postgres vs MySQL).
  • Startup migrations: If allowed by AUTO_MIGRATE and NODE_ENV, the API runs pending migrations before accepting HTTP connections (see packages/db/src/migrate.ts).
  • Manual CLI: Use package scripts db:migrate:pg / db:migrate:mysql when you prefer migrations outside the API process (e.g. CI).

Dialect notes and CLI detail: database.md.

Running locally

From repo root, typical development commands:

Command Starts
pnpm dev:all Web + API + worker in parallel after pnpm db:migrate (Vite + Fastify + BullMQ). Requires DB + Redis; configure VITE_API_BASE_URL when API port differs.
pnpm db:migrate Apply pending SQL migrations via @starter/db (used by dev:all).
pnpm build:ci pnpm verify then full workspace build (CI-style gate).
pnpm test:e2e Playwright smoke tests (login, CRM create, super-admin); run pnpm test:e2e:install once for Chromium.
pnpm --filter @starter/api dev Fastify API (tsx watch)
pnpm --filter @starter/worker dev BullMQ worker
pnpm --filter @starter/web dev Vite dev server for the React app
pnpm --filter @starter/mobile start Expo dev tools / bundler
pnpm -r typecheck Type-check all workspace projects
pnpm verify Typecheck + tests (recommended before PRs)
pnpm -r test Run tests where defined

Docker Compose

docker-compose.yml defines Redis, optional Postgres or MySQL (profiles), and builds for the API and worker. Provide env via .env; align database settings with the profile you enable.

Security highlights

  • Helmet, CORS, and rate limiting on the API (see apps/api/src/index.ts); webhook routes may be allow-listed from aggressive throttling — verify in source when hardening.
  • Passwords hashed with Argon2; refresh tokens never stored in plaintext.
  • Optional field-level encryption for sensitive columns via @starter/crypto (AES-256-GCM).
  • Never commit .env; rotate secrets for production.

Checklist and threat-oriented guidance: security.md.

Platform billing (Stripe)

Realm subscriptions can integrate with Stripe for customer records, embedded card capture (SetupIntent + Elements), and webhooks that update subscription / ledger state. Product behavior and schema are documented in architecture.md (realm subscriptions, payment ledger, baseline shipped).

Configure & webhooks

  • Enter the platform Stripe secret key and webhook signing secret in Super Admin → Integrations → Payments (encrypted at rest via existing field encryption). The UI shows the public webhook URL pattern: {API_BASE_URL}/webhooks/stripe.
  • In the Stripe Dashboard, point webhooks at that URL and subscribe to the event types suggested in the same screen (e.g. setup and payment intent outcomes).
  • Stripe publishable key is returned to authorized clients only for SetupIntent flows — do not embed long-lived secrets in the SPA.

Operational notes

  • Apply SQL migration 0030_subscription_psp_and_dunning (and prior subscription migrations) on every environment; confirm AUTO_MIGRATE or your CI migration job.
  • After enabling Stripe, new realm subscriptions create/link a Stripe Customer; subscribers manage cards from Admin → Subscription or Settings → Subscription.
  • Workers that create PaymentIntents should persist psp_payment_intent_id and set Stripe metadata for correlation — see architecture doc baseline paragraph.

Developer

Navigate, extend, keep contracts aligned

How to read this repo

Treat the API as the system of record: authentication, authorization, tenant boundaries, validation, and persistence. Web and mobile apps are clients; they should not duplicate business rules beyond UX-level checks. Shared Zod schemas in @starter/shared are the contract layer so TypeScript types and runtime validation stay aligned across processes.

Onboarding path: skim this page → open architecture.md for data flow → use the directory map below when jumping into code → run pnpm verify before pushing.

Directory map

High-level layout of the pnpm workspace (see also root README.md and architecture.md).

Applications (apps/)

Path Responsibility
apps/api Fastify HTTP server: route modules under src/routes/, plugins and bootstrapping in src/index.ts, env in src/env-bootstrap.ts, cross-cutting helpers in src/lib/. Registers JWT, tenant resolution, rate limits, raw-body webhooks where needed.
apps/worker BullMQ consumers; queue names must match API producers. Long-running billing jobs belong here, not in request handlers.
apps/web Vite + React + Tailwind SPA: pages under src/pages/, layouts, shared UI components, client fetch helpers.
apps/mobile Expo app; uses EXPO_PUBLIC_* env; SecureStore (or equivalent) for refresh token storage patterns.

Packages (packages/)

Package Responsibility
@starter/db Drizzle schema (src/*-schema.ts), repository modules (src/*-repos.ts), migration runners, database-url.ts. No HTTP — pure data access and invariants enforced in SQL/TS.
@starter/shared Zod schemas, shared DTO shapes, billing math — imported by API and clients to prevent drift.
@starter/crypto AES-GCM helpers for field-level encryption; used when persisting integration secrets and sensitive columns.
@starter/logger Pino-based logging wrapper; prefer over console.log in API and worker.

Request & module flow

  • Entry: apps/api/src/index.ts builds the Fastify instance, registers CORS, security plugins, rate limiting, JWT, and route families (tenant, account, platform, webhooks).
  • Routes: each file under apps/api/src/routes/ should own one bounded HTTP surface (e.g. tenant-sales.ts, tenant-crm.ts); keep handlers thin — parse → validate with shared Zod → call repo → map DTO. Prefix map: modules-index.md.
  • Tenant context: middleware attaches realm user + tenant_id from JWT; repositories in @starter/db must scope queries so cross-tenant reads/writes cannot occur.
  • Platform vs realm: super-admin routes use separate auth context (null tenant_id users); do not mix guards accidentally.

Data layer & migrations

  • ORM: Drizzle with explicit SQL migrations checked in under packages/db/drizzle/pg and packages/db/drizzle/mysql — both dialects must stay logically equivalent for portable features.
  • Repos: prefer query functions colocated with tables (e.g. crm-repos.ts, sales-funnel-*-repos.ts) over ad-hoc SQL in routes — easier to test and audit for tenant filters.
  • Migrations: generate with Drizzle Kit from schema edits; apply via API boot (AUTO_MIGRATE) in dev or CI/CD steps in production.
  • Subscriptions / payments: ledger in platform_subscription_payments; PSP correlation columns (psp_*) and subscription dunning fields ship with migration 0030 — see architecture.md.

Relationship notes

  • Tenant scope — crm_*, sales_funnel_*, and workforce_* rows include tenant_id and should only be queried through tenant-scoped repositories.
  • Users — Realm users belong to one tenant; super_admin users have tenant_id = NULL. tenant_user_module_roles grants per-module roles (CRM, sales, workforce).
  • CRM graph — crm_relationships connects organizations and contacts via configurable crm_relationship_types; activities attach polymorphically to a related entity.
  • Sales funnel — BDR leads and pipeline deals optionally link to crm_organizations; contacts attach through junction tables; promoting a lead sets promoted_from_lead_id on the deal.
  • Subscriptions — subscriptions bill a tenant (organization-wide) or a single user_id per plan billing_scope; payments append to platform_subscription_payments.

Table-level map for HTTP modules: modules-index.md. Domain guide: sales-funnel-module.md.

Shared contracts & validation

  • Put request bodies and cross-cutting types in packages/shared; export Zod schemas and use z.infer in API and UI.
  • Server wins: always re-validate on the API — client validation is UX only.
  • When adding an HTTP surface, add or extend a schema first so mobile and web cannot drift from the API.

Convention detail: best-practices.md.

Background jobs (BullMQ)

  • Queue names follow {prod|dev}-<purpose>; do not use : in names (BullMQ restriction).
  • Producer helpers live in API src/lib/; consumer registration in apps/worker/src/index.ts.
  • For subscription billing: separate queue from email, chunked jobs, deterministic jobId, DB idempotency guards — see best-practices.md (subscription payment generation).

Web & mobile clients

  • Vite: loads env from repo root; VITE_API_BASE_URL defaults from API_PORT (legacy PORT) when unset — see development.md.
  • UI: reuse AppShell layouts and Tailwind patterns; prefer extending existing components over one-off page markup.
  • Web routes (apps/web): public /login, /signup; /super-admin/* (users, jobs, integrations, subscriptions, features, mail); /admin/* (users, system, CRM, sales, workforce); /user/* (profile, CRM). Optional modules are gated (*ModuleGate) by tenant feature flags — see sales-funnel-module.md.
  • Expo: public config via EXPO_PUBLIC_*; persist refresh tokens securely — see mobile-devices.md.

API contract & ops

  • Versioned JSON API: /v1/* only (no legacy unprefixed mounts).
  • OpenAPI (Zod-derived starter surface): GET /openapi.json and Swagger UI at /docs on the API origin (e.g. http://localhost:3500/docs when running locally). Sync committed spec: pnpm --filter @starter/api openapi:sync.
  • Probes: GET /health, GET /ready; metrics: GET /metrics (starter_http_requests_total).
  • Request correlation: X-Request-Id on requests and responses.

ADRs: 001-api-versioning, 002-refresh-cookie-csrf.

Quality gates & CI

  • pnpm verify — typecheck + tests across workspaces (pre-PR default).
  • pnpm build:ci — verify then full build graph (CI-style).
  • Prefer unit tests beside pure logic (packages/shared, packages/crypto, parsers); keep route tests focused on HTTP integration where needed.

Runner matrix and TDD notes: testing.md.

Source documentation standards

Every source file in the monorepo carries a file header (purpose, responsibilities, dependencies, security notes) and TSDoc/JSDoc on exported symbols. The canonical rules live in source-documentation.md — use it when adding routes, repos, components, or shared contracts.

Layer What to document Where
File Why the file exists, responsibilities, major dependencies, security/tenant scope, extension points Block comment before imports
Exports Purpose, params, returns, throws, side effects, performance/security when non-obvious TSDoc on functions, types, components, hooks
Cross-cutting rules Architecture, env, testing, collaboration gates guidelines/ (not duplicated in every file)
Feature behaviour Product decisions, statuses, permissions docs/*-module.md

By workspace area

  • apps/api — Route modules: URL prefix, auth guard, Zod entrypoints, repos called. lib/: side effects (queues, email, storage), tenant/platform scope.
  • packages/db — Tables touched, tenant_id filters, field encryption boundaries, transaction assumptions.
  • packages/shared — Domain meaning of Zod schemas and DTOs; consumers (API, web, mobile).
  • apps/web — Component purpose, props, shell/layout conventions (AppShell carries page title — no duplicate h1).
  • packages/crypto — Cipher scope, AAD binding, key material — never log plaintext or keys.
Assistants: read AGENTS.md first, then source-documentation.md when touching source. Update headers in the same change as behaviour edits.

Conventions & extending safely

  • Documentation: file headers + export TSDoc per source-documentation.md; cross-cutting updates in docs/guidelines/ (see guidelines/README.md).
  • Coding assistants: start at AGENTS.md (repo root), then guidelines/README.md and .cursor/rules/.
  • AI / structural changes: read prompt-principles.md — structural topology (extra apps, proxies, dual React trees) needs explicit approval before scaffolding.
  • Product AI (future): not shipped; see ai-harness-checklist.md and ADR 004 before adding in-app LLM features.
  • Security: follow security.md for secrets, logging, and tenant isolation reviews.
  • Vocabulary: keep terms aligned with code and glossary.md.
